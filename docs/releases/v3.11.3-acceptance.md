# 3.11.3 verification

All annotation-changing checks use isolated disposable projects, not user projects. The production frontend build, 336 backend tests and 163 frontend tests passed locally.

## Shared person deletion (#8)

Browser and backend checks cover unlinked and linked people, cancel/confirm, Undo/Redo, stale confirmations and failed saves. Removing the shared identity preserves each camera's local track IDs, geometry and annotation state.

## Decoded-frame storage (#9)

Checks cover cache sizes, selected-video clearing, active workspace/job rejection, unchanged source videos, annotations, operation history, revisions and frame ledgers. Reopening regenerates the exact frame sequence. Changed/missing sources are rejected before clearing; a crash between directory rename and database commit is recoverable. Detached cache directories are removed only after a verified rebuild.

A manual in-app browser check verified the storage column, selection, confirmation details and cancellation. The screenshot is saved locally as `.frameinsight/qa/frame-storage-3.11.3.jpg`.

## Frame presentation (#10)

Chrome pixel checks exercise delayed, failed and out-of-order frame responses in the editor and passive camera tiles. The last decoded image and its own overlays stay together until the next pair is ready; pending frames reject edits. Slow playback traverses all 24 numbered fixture frames without blanking a loaded preview. Manual playback at 0.5× also completed on the disposable fixture.

## Consecutive corrections (#11)

A synthetic 20-track project with 40,600 observations exercises successive corrections, interpolation, ordered server revisions, exact Undo/Redo and unchanged-record reuse. Tests also cover immutable delayed recovery writes, legacy unscoped gaps with classes in another camera, cross-video ID conflicts, and frame-index inheritance.

The synchronous store-edit benchmark improved from approximately 1.7–2.1 seconds per edit to 33–61 milliseconds on this development machine. These are store-call measurements, not a guarantee of full browser latency or performance on other hardware. A separate headless Chrome run performed eight real pointer drags on the 40,600-observation fixture. All eight changes saved on the intended track, with matching coordinates and unchanged annotation count. Estimated paint latency was 197–511 ms; the eight gestures dispatched in 4.75 seconds. Browser recovery writes and the background server save queue still take measurable time. The earlier browser baseline ran alongside the full suite, so it is not a controlled speed comparison. Local evidence: `.frameinsight/qa/issue11-ui-benchmark-after.json` and `.png`.

The track-class catalog is tested to visit all 40,600 observations once regardless of track count. Label memoization checks every visual and hit-target field; badge borders avoid unnecessary full-stage shadow buffers.

A delayed-save browser regression also covers creating a camera track and immediately drawing its first box. Tool selection happens before the asynchronous save, so its completion cannot finish an in-progress gesture.

The full local Chrome run covered the existing workflow plus all new frame/cache/person checks. One optional real-user-video check is skipped when that fixture is unavailable. The final asynchronous track-creation fix is additionally exercised by a gated-save regression and 22 passing focused multi-camera/frame-presentation tests. The gated test reproduced the missing box on the old build and passed on the rebuilt fix.
