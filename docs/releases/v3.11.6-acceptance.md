# 3.11.6 verification

All changes and mutation checks use disposable test projects. The reporter's original project and crash logs were not supplied. Physical Windows 11 testing is not claimed.

## Reproduced issue #12

The new delayed-operation Chrome regression fails against the unmodified 3.11.4 code: the camera header claims Saved while an annotation POST is held open. A second run bypassing that first assertion also fails because creating a shared person remains blocked behind that annotation POST.

The fixed build passes: while the POST remains pending, frames advance exactly to 1, 2 and 3; shared person 17 is saved independently; both save indicators remain accurate; releasing the POST saves the expected geometry; no delayed cursor jump or stale saving error appears; reload retains the saved box. Existing checks also cover pending new-track assignments, failed saves blocking Finish, retries, deletions and Undo.

## Recovery safety

Browser recovery stores an immutable checkpoint plus individual immutable operation records, with small ID lists for pending edits and undo/redo. Checkpoints rotate after 1,000 operations; old checkpoints remain until explicit project cleanup because another open tab may still need them. Completed projects from older installations can still read their full-snapshot journals. The annotation JSON format is unchanged.

Tests cover exact recovery, lost acknowledgements, interrupted journal writes and retry, checkpoint rotation, legacy journals, missing records, and project cleanup that preserves other projects. Existing store tests continue to exercise failed recovery, rejected operations, exact Undo/Redo, settings changes and deleted/stale tabs. Explicit Save shares the in-flight pump and waits for completion without inventing a 30-second save failure. A unit test advances the wall clock by two minutes during a pending acknowledgement and confirms editing/navigation remain possible and Save completes after acknowledgement.

## Performance evidence

A disposable synthetic session uses 12 cameras, 41 shared people, 736 frames per camera, 48 local tracks and 35,328 observations with two classes. Additional frame timestamps and repeated numbered-fixture PNGs are synthetic; this is a UI workload, not a real training recording. Five consecutive ten-pixel pointer drags at frame 60 each immediately advance and return one frame. Both versions use the same fixture, focus settings, machine and Chrome viewport in separate sequential runs; recovery is warmed before measurement.

| Measurement | 3.11.4 | Fixed build |
|---|---:|---:|
| Five edits and frame navigation dispatched | 1,879 ms | 1,017 ms |
| All five edits acknowledged | 4,711 ms | 2,810 ms |
| Total synchronous IndexedDB put work | 803 ms | 2.4 ms |
| Per-edit plus next/previous-frame roundtrip | 275–327 ms | 139–197 ms |

Both runs verify all five revisions, expected saved coordinates, unchanged observation counts and no browser exceptions. The measurements demonstrate reduced work on this machine; they do not guarantee the reporter's Windows timings or establish the cause of an unlogged crash. Local evidence is under `.frameinsight/qa/issue12/`, including before/after JSON, screenshots and fixture/benchmark scripts.

Live status now reads project revision and video metadata without reading annotation entities. A backend regression verifies this independently of annotation JSON decoding. Camera appearance strips consume one annotation pass, and backend gap checks consider the observation's own track rather than every camera's gaps.

## Acceptance

The production frontend build, 173 frontend tests, 348 backend tests pass. Nineteen focused Chrome checks passed for the autosave/recovery change; five final settings/save/reload checks also pass after the inactive-project fix, covering 22 distinct browser scenarios overall. Manual computer-use verification on the disposable 12-camera project corrected a box at frame 351, advanced immediately to 352, and confirmed both save indicators reached Saved. Screenshot: `.frameinsight/qa/issue12/manual-after.png`.

One initial browser run overlapped a production rebuild; its final reload received the temporary build-unavailable response. Re-running that JSON replacement/reload/Undo test after the build completed passed without application changes.

Publication requires the full CI browser suite and native Windows/Debian installer, upgrade/data-preservation and uninstall acceptance in the desktop release workflow.

## Superseded build

The initial v3.11.5 tag was withdrawn before publication when final review found that an inactive-project settings write could retain compact-journal markers on a full snapshot. Version 3.11.6 strips those markers and recognizes already-materialized snapshots during reading; two new unit regressions and an end-to-end Chrome settings/reload regression cover this path. The release workflow requires an existing remote tag, so the withdrawn build cannot publish through its verify-tag release step.
